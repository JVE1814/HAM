## Why this matters

Three routes of the customer page take a record's sys_id from the caller: report a fault, confirm
a self-install, and answer an attestation. None of the handlers compares the record's Customer with
the caller's. What keeps Customer B's admin away from Customer A's records is the before-query
visibility rules (ADR 0005), plus one check in the attestation code. Confirming an install moves
units toward service, where billing starts, so a gap here lets one Customer start another's billing.

No test proves it. The fake Glide the unit tests run on "runs no business rule, ACL or flow"
(`README.md:323`), so a unit test cannot. ATF covers only the returns route across Customers
(`customerReturnRequestTest`, `src/fluent/returns/tests.now.ts:123`).

This plan adds one ATF test to suite **NaaS - P2**. As Customer B's admin it calls the three
handlers with Customer A's sys_ids and checks that each is refused and that nothing changed. It
then repeats the calls as Customer A's admin, which shows the records were real and reachable. The
plan changes no server code. **If the test fails on an instance, that is a finding to report, not
a defect to fix in this plan.**

### How the existing route tests work

ATF's REST step cannot sign in from this scope, so a route test calls the route's handler from a
**Run Server Side Script** step, as the impersonated user, with stand-in request and response
objects. The pattern to copy is the audit scan test in the same file
(`src/fluent/shared/visibility-tests.now.ts:326-376`). It defines three helpers inside the script:
`call(handler, data, pathParams)`, `find(table, query, pastRules)` and
`expectReply(what, reply, status, error)`. `find` with `pastRules` true reads past the app's
before-query rules through `platform/beyond-visibility.ts`, as the app's own server logic does. The
new test uses that to get Customer A's sys_ids while it runs as Customer B's admin.

A script is plain text to the build, so `src/server/built-metadata.test.ts:1378-1533` checks each
built script. The new scripts must keep to these rules:

- Every module is loaded as `var name = require('x_daas_ham/naas-ham/<version>/src/server/<path>.ts')`, the path must be a module the build installs, and every `name.something` in the script must be a function that module exports.
- `<version>` is the `version` in `package.json` (`0.1.0` at `1864b17`).
- A script holds no step output (`${step.record_id}`). The platform does not fill one in inside a script. A script finds its fixtures by name instead.
- The unit test runs each script against stand-ins that answer every handler call with HTTP 599. The script must return `true` or `false`. When it returns `false`, its output message must contain `expected HTTP`. The message must never contain `undefined`, `TypeError` or `is not a function`.
- Every ATF test is in exactly one suite, has a unique name of at most 100 characters and a description of at most 1000.

Rules for `.now.ts` files (`README.md:324-329`): they hold constants, template literals over
constants, and imports of constants from `src/server/domain`. No function call, loop, spread or
array element. A step's field value takes a named constant, not a property access, which is why
the file declares `const IN_USE = INSTALL_STATUS.inUse` and the like at its top. A new Fluent
record uses `$id: Now.ID['...']` with a name no other record has.

### Why the test is built this way

- **The Order is at stage installing.** Then it waits for the confirmation whatever the caller can see of its units. With a held-back stage the handler would also refuse Customer B because B cannot count A's shipped units, and the test could not tell a broken Order rule from a working one.
- **A fourth call uses Customer B's own attestation with Customer A's item.** That is the only way to reach the check at `attestations.ts:121`. The handler answers HTTP 200 and must skip the item.
- **The control calls as Customer A's admin are loose for the fault and the install.** They assert only that the device and the Order were found (not HTTP 404, not HTTP 409). Whether a Customer admin's case insert and unit move then succeed has not been verified on an instance for a user with that single role, and is not what this test is about. The attestation control asserts HTTP 200 and that the answer was saved, which proves the earlier "unanswered" check could have failed.

## Maintenance notes

- A new customer route that takes a sys_id from the caller needs a call in both scripts of this test, refused for Customer B and found for Customer A.
- The scripts spell out the installed module path, which names the version in `package.json`. After a version change `built-metadata.test.ts` fails until the four `require` paths are updated (`docs/verify-on-instance.md`, "ATF route tests").
- The fault and install controls are loose on purpose (any status but 404, any but 409). Once a Customer admin with that single role has been verified on an instance, tighten them to HTTP 201 and HTTP 200.
- An attestation item has no before-query rule. The check at `src/server/platform/attestations.ts:121` is the only thing between a Customer admin and another Customer's item, and only this ATF test covers it. A unit test of `saveAttestationAnswers` on the fake Glide would cover it locally. It is left out here because plan 008 creates `src/server/platform/attestations.test.ts`. Add it there once plan 008 has landed.
